**Database:** PostgreSQL\
**ORM:** Prisma\
**Related documents:** `prd.md`, `requirements.md`, `architecture.md`,
`user-flow.md`

## 1. Purpose

Define the MVP relational data model, constraints, indexes, deletion
behavior, and migration requirements for the URL Shortener.

The schema prioritizes: - Unique short codes. - Strong user ownership
boundaries. - Reliable link lifecycle behavior. - Efficient redirect
lookup. - Basic click analytics. - Minimal collection of visitor data.

## 2. Schema Overview

MVP entities:

1.  `User` --- registered account.
2.  `Link` --- short URL and destination owned by a user.
3.  `ClickEvent` --- click event associated with a link.

Authentication session storage depends on the selected auth strategy. If
server-side sessions are used, add a session table or use a supported
session store. Do not store raw session tokens.

## 4. PostgreSQL Tables

### 4.1 `users`

Stores registered accounts.

  -----------------------------------------------------------------------
  Column            Type              Null              Constraints /
                                                        notes
  ----------------- ----------------- ----------------- -----------------
  `id`              UUID              No                Primary key;
                                                        generated by
                                                        application or
                                                        database

  `email`           VARCHAR(320)      No                Unique;
                                                        normalized before
                                                        persistence

  `password_hash`   VARCHAR(255)      No                Password hash
                                                        only; never
                                                        plaintext

  `role`            VARCHAR(32)       No                Default 'USER';
                                                        Enum: USER, ADMIN
                                                        for RBAC/admin ops

  `created_at`      TIMESTAMPTZ       No                Default current
                                                        timestamp

  `updated_at`      TIMESTAMPTZ       No                Updated on
                                                        account changes
  -----------------------------------------------------------------------

Constraints: - Unique normalized email. - Email normalization policy
must be consistent in registration and login. - Role defaults to USER. - Do not assume every
email provider uses the same alias semantics; do not strip dots or
plus-tags globally. - Password hash algorithm and work factor are
configured by the authentication implementation.

Indexes: - Unique index on normalized `email`.

### 4.2 `links`

Stores short links.

  Column              Type          Null   Constraints / notes
  ------------------- ------------- ------ -----------------------------------
  `id`                UUID          No     Primary key
  `user_id`           UUID          No     Foreign key to `users.id`
  `code`              VARCHAR(32)   No     Unique short code or custom alias
  `destination_url`   TEXT          No     Validated HTTP/HTTPS destination
  `is_active`         BOOLEAN       No     Default `true`
  `expires_at`        TIMESTAMPTZ   Yes    Null means no expiration
  `created_at`        TIMESTAMPTZ   No     Default current timestamp
  `updated_at`        TIMESTAMPTZ   No     Updated on mutation

Constraints: - `code` unique globally. - `user_id` references an
existing user. - `code` must match the configured allowed character set
and length. - `destination_url` must be non-empty. - Application
validation must enforce HTTP/HTTPS schemes. A database check may enforce
basic non-empty requirements, but full URL validation belongs in the
application. - Expiration may be null; if non-null, it is interpreted in
UTC. - `is_active` is independent of expiration. Redirect eligibility
requires both active and not expired.

Indexes: - Unique index on `code` --- required for redirect lookup. -
Index on `(user_id, created_at DESC)` --- dashboard listing. - Optional
index on `(user_id, is_active, created_at DESC)` --- only if query
patterns justify it. - Avoid adding indexes before validating actual
query plans.

### 4.3 `click_events`

Stores click events for basic and aggregated analytics.

  Column         Type           Null   Constraints / notes
  -------------- -------------- ------ ---------------------------
  `id`           UUID           No     Primary key
  `link_id`      UUID           No     Foreign key to `links.id`
  `clicked_at`   TIMESTAMPTZ    No     Default current timestamp
  `referrer`     VARCHAR(512)   Yes    Referrer domain / URL string
  `device_type`  VARCHAR(64)    Yes    e.g. desktop, mobile, tablet
  `country_code` VARCHAR(2)     Yes    ISO 3166-1 alpha-2 code

Privacy decision:
- Do not persist raw IP addresses.
- Do not persist full raw user-agent strings or identifiable visitor fingerprints.
- Extract sanitized `device_type` (desktop, mobile, tablet) and geographic `country_code` from headers (e.g. Cloudflare CF-IPCountry) without logging raw IPs.
- Document purpose, retention, access, and deletion behavior.

Indexes: - Index on `(link_id, clicked_at DESC)` --- link analytics. -
Index on `(clicked_at)` only if retention cleanup or time-range queries
need it. - If the application frequently aggregates daily counts across
many links, evaluate a rollup table rather than relying on unbounded
event scans.

Foreign key: - `link_id` references `links.id`. - Recommended MVP
deletion behavior: cascade click-event deletion when the link is
hard-deleted. If the product chooses analytics retention after link
deletion, use a documented soft-delete/anonymization strategy instead.

## 5. Ownership and Authorization

Ownership is represented by `links.user_id`.

Every link-management query must scope by both the link identifier and
the authenticated user identifier. Example conceptual query:

``` sql
SELECT *
FROM links
WHERE id = $1
  AND user_id = $authenticated_user_id;
```

Do not accept `user_id` from the client as the authorization source.

For create operations: - Derive `user_id` from the authenticated
session. - Ignore or reject client-supplied ownership fields. - Persist
ownership in the same transaction as link creation.

For analytics: - Verify ownership before returning events or
aggregates. - Do not expose raw event rows to a user unless explicitly
required.

## 6. Link Code Design

### 6.1 Code rules

-   Generated code and custom alias use the same `code` column.
-   Codes are globally unique.
-   Configure an allowed character set, such as ASCII letters and
    digits.
-   Define minimum and maximum length in application validation.
-   Reserve application routes and system words, such as `login`,
    `register`, `dashboard`, `api`, `admin`, `health`, and `favicon`.
-   Case sensitivity must be consistent across generation, validation,
    database comparison, and redirect lookup.

Recommended MVP: - Use case-sensitive Base62 codes if the deployed
database collation and routing preserve case. - If case-insensitive
routing is desired, normalize codes to lowercase and use a
lowercase-safe alphabet instead. - Do not change code normalization
after launch without a migration and compatibility plan.

### 6.2 Collision handling

-   Database unique constraint is the final authority.
-   On generated-code collision, retry with a new code a bounded number
    of times.
-   Custom alias collision returns a validation conflict.
-   Do not rely on a pre-insert existence check alone; concurrent
    requests can race.

## 7. Deletion and Retention Policy

### 7.1 Recommended MVP

Hard-delete link and click events when the owner deletes a link: -
`links` row is deleted. - Associated `click_events` are deleted through
`ON DELETE CASCADE`. - The short code becomes available again only if
the product explicitly allows code reuse.

**Recommended code reuse policy:** do not reuse deleted codes
immediately. This avoids an old shared URL unexpectedly pointing to a
different destination. Implement tombstones or soft deletion if code
reservation is required.

### 7.2 Alternative: soft deletion

If link audit or code reservation is needed, add: -
`deleted_at TIMESTAMPTZ NULL` - Optional `deleted_by` field if admin
actions are later supported.

Then: - Exclude deleted links from dashboard default queries. - Return
not found for deleted links in redirect resolution. - Keep or purge
analytics according to retention policy. - Ensure unique code constraint
still reserves deleted codes.

This decision must be finalized before implementing deletion.

## 8. Analytics Strategy

### 8.1 MVP event recording

On a valid redirect: 1. Resolve link by code. 2. Check active and
expiration state. 3. Respond with redirect. 4. Record click event
synchronously or enqueue it, based on the implementation's reliability
and latency goals.

If click recording is asynchronous: - Use a durable queue or
accepted-loss policy. - Monitor queue failures and backlog. - Redirect
should not wait indefinitely for analytics.

If click recording is synchronous: - Keep the insert minimal. - Measure
redirect latency under load. - Define behavior when the analytics insert
fails.

### 8.2 Aggregation

For MVP: - Total clicks can be calculated using `COUNT(*)` by
`link_id`. - If event volume grows, add a daily rollup table, for
example `link_click_daily(link_id, date, click_count)`. - Rollup
uniqueness should be `(link_id, date)`. - Rollup updates must be
idempotent or use an aggregation pipeline that avoids double counting.

### 8.3 Retention

Define before production: - Click-event retention period. - Scheduled
cleanup method. - Whether aggregate totals survive event deletion. -
Whether link deletion removes aggregate data. - How user deletion
affects links and analytics.

Do not retain analytics indefinitely by default.

## 9. Prisma Model Draft

This is a starting schema. Confirm the selected Prisma version and
authentication strategy before applying migrations.

``` prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

enum UserRole {
  USER
  ADMIN
}

model User {
  id           String   @id @default(uuid()) @db.Uuid
  email        String   @unique @db.VarChar(320)
  passwordHash String   @map("password_hash") @db.VarChar(255)
  role         UserRole @default(USER)
  createdAt    DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt    DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  links Link[]

  @@map("users")
}

model Link {
  id            String   @id @default(uuid()) @db.Uuid
  userId        String   @map("user_id") @db.Uuid
  code          String   @unique @db.VarChar(32)
  destinationUrl String   @map("destination_url") @db.Text
  isActive      Boolean  @default(true) @map("is_active")
  expiresAt     DateTime? @map("expires_at") @db.Timestamptz(6)
  createdAt     DateTime @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt     DateTime @updatedAt @map("updated_at") @db.Timestamptz(6)

  user        User         @relation(fields: [userId], references: [id], onDelete: Restrict)
  clickEvents ClickEvent[]

  @@index([userId, createdAt(sort: Desc)])
  @@index([expiresAt])
  @@map("links")
}

model ClickEvent {
  id          String   @id @default(uuid()) @db.Uuid
  linkId      String   @map("link_id") @db.Uuid
  clickedAt   DateTime @default(now()) @map("clicked_at") @db.Timestamptz(6)
  referrer    String?  @db.VarChar(512)
  deviceType  String?  @map("device_type") @db.VarChar(64)
  countryCode String?  @map("country_code") @db.VarChar(2)

  link Link @relation(fields: [linkId], references: [id], onDelete: Cascade)

  @@index([linkId, clickedAt(sort: Desc)])
  @@map("click_events")
}
```

### Prisma notes

-   Verify the exact Prisma syntax for the pinned version before
    migration.
-   Prisma `@updatedAt` handles update timestamps through Prisma Client;
    direct SQL updates must also maintain `updated_at`.
-   If using email normalization, store normalized email in the unique
    field or add a separate canonical field. Do not depend on
    case-sensitive uniqueness alone.
-   UUID generation can be application-side or database-side, but choose
    one consistently.
-   `onDelete: Restrict` for users prevents accidental user deletion
    while links remain. User deletion should be implemented as a
    deliberate service operation. Alternatively, `Cascade` can be used
    if hard deletion of a user account is intended to wipe all owned links.
-   For hard link deletion, `ClickEvent` cascade is intentional.
-   Consider adding `createdAt` and `updatedAt` indexes only when
    justified by query plans.

## 10. SQL Migration Reference

Representative PostgreSQL DDL:

``` sql
CREATE TYPE user_role AS ENUM ('USER', 'ADMIN');

CREATE TABLE users (
  id UUID PRIMARY KEY,
  email VARCHAR(320) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  role user_role NOT NULL DEFAULT 'USER',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE links (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  code VARCHAR(32) NOT NULL UNIQUE,
  destination_url TEXT NOT NULL,
  is_active BOOLEAN NOT NULL DEFAULT true,
  expires_at TIMESTAMPTZ NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT links_code_nonempty CHECK (length(code) > 0),
  CONSTRAINT links_destination_nonempty CHECK (length(destination_url) > 0)
);

CREATE INDEX links_user_created_idx
  ON links (user_id, created_at DESC);
CREATE INDEX links_expires_at_idx
  ON links (expires_at);

CREATE TABLE click_events (
  id UUID PRIMARY KEY,
  link_id UUID NOT NULL REFERENCES links(id) ON DELETE CASCADE,
  clicked_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  referrer VARCHAR(512) NULL,
  device_type VARCHAR(64) NULL,
  country_code VARCHAR(2) NULL
);

CREATE INDEX click_events_link_clicked_idx
  ON click_events (link_id, clicked_at DESC);
```

This SQL is illustrative. Prisma migrations should be the canonical
source after schema review.

## 11. Query Patterns

### Resolve redirect

``` sql
SELECT id, destination_url, is_active, expires_at
FROM links
WHERE code = $1;
```

The unique index on `code` should make lookup efficient.

### List a user's links

``` sql
SELECT id, code, destination_url, is_active, expires_at, created_at
FROM links
WHERE user_id = $1
ORDER BY created_at DESC
LIMIT $2 OFFSET $3;
```

Use cursor pagination instead of offset pagination if list size or page
depth becomes large.

### Count clicks for a link

``` sql
SELECT COUNT(*)
FROM click_events
WHERE link_id = $1;
```

Only execute after verifying link ownership.

### Count clicks in a time range

``` sql
SELECT COUNT(*)
FROM click_events
WHERE link_id = $1
  AND clicked_at >= $2
  AND clicked_at < $3;
```

Use UTC boundaries and half-open intervals `[start, end)`.

## 12. Migration and Seed Requirements

-   Use version-controlled Prisma migrations.
-   Never edit a migration that has already been applied in shared or
    production environments.
-   Review generated SQL for destructive operations.
-   Run migrations in staging before production.
-   Back up production before risky schema changes.
-   Use a dedicated migration command in deployment.
-   Avoid running migrations independently from every application
    instance.
-   Seed only development/test data; never seed default production
    credentials.
-   Ensure migration and seed commands are idempotent where practical.

## 14. Operational Requirements

-   Monitor database connection failures, query latency, pool
    saturation, and storage growth.
-   Track click-event volume and retention cleanup.
-   Alert on failed migrations and backup failures.
-   Test restoration from backup.
-   Review slow query logs and `EXPLAIN ANALYZE` for critical queries.
-   Do not add Redis or analytics rollups until measured workload
    requires them.

## 15. Schema Evolution

### Add a field

1.  Add field in Prisma schema.
2.  Generate migration.
3.  Review SQL.
4.  Deploy migration safely.
5.  Update application validation and API contracts.
6.  Backfill if required.
7.  Remove compatibility code only after rollout.

### Change code format

-   Preserve existing codes.
-   Add new validation for future codes.
-   Ensure old codes remain resolvable.
-   Do not mass-rewrite short URLs without a compatibility plan.

### Add custom domains later

Potential future entity: - `Domain`: domain ownership, verification
state, configuration. - `Link` may include domain reference or use
domain+code uniqueness. - Redirect resolution must validate host and
code together. - Do not add this to MVP without product approval.

### Add teams later

Potential future entities: - `Workspace` - `WorkspaceMember` - Workspace
roles and permissions. - Link ownership migration from user to
workspace. - Audit events.
